# Upload limits and privacy feedback — 8 September 2026

## Implemented

1. **Make upload limits visible on laptops.** A dedicated notice immediately below
   the File upload heading displays the current per-file limit before file
   selection: 100 MB as a guest, 3 GB after sign-in. Guests can open sign-in from
   the notice. The same notice is used on mobile and desktop; the mobile intro
   also explains both limits before the upload step. The underlying limits remain
   100 MiB / 3 GiB; MB / GB retain the existing UI convention.
2. **Explain private storage and sharing before upload.** The compact privacy
   notice explains link access, administrator access and what deletion does.
   The privacy page repeats these facts and describes activity notifications.
3. **Explain actual file checks.** Upload copy names automatic format and size
   checks. Share screens state that anyone with the link can download the file.
   The privacy page distinguishes approval from content certification or redaction.

## Claims that require new capabilities

- **“AI filters every file.”** Not implemented. `DeterministicDocumentClassifier`
  is enabled for `local`, `test` and `v0-prod` and returns `APPROVED`.
  `DocumentProcessingService` passes an empty string to it. Current upload
  validation checks MIME, size and a file-header signature; it does not classify
  aviation relevance or redact confidential material.
- **“Only the uploader and recipient can read files.” / end-to-end encryption /
  zero knowledge.** Not implemented. `TelegramAdminCommandService` can create
  signed downloads for administrators; the service can read stored files.
  Private storage and signed links do not prevent operator access.
- **“Only the named recipient can open a share link.”** Not implemented. The
  public share endpoint grants access based on possession of the link, without
  recipient authentication. A forwarded link grants the same access.

These features need separate product decisions: which content to filter, whether
an external AI provider may receive file contents, and whether recipient identity
or client-side encryption is required. They cannot be delivered by changing copy.

## Evidence in this repository

- `apps/backend/src/main/kotlin/ae/fly/backend/document/DocumentService.kt`:
  owner checks, size limits, storage deletion and share-token revocation.
- `apps/backend/src/main/kotlin/ae/fly/backend/upload/UploadService.kt`:
  stored-object size, MIME and header validation.
- `apps/backend/src/main/kotlin/ae/fly/backend/share/ShareController.kt`:
  public token resolution and signed downloads.
- `apps/backend/src/main/kotlin/ae/fly/backend/auth/TelegramAdminCommandService.kt`:
  administrator file access.
- `apps/backend/src/main/kotlin/ae/fly/backend/upload/UploadNotifier.kt` and
  `share/ShareAccessNotifier.kt`: activity metadata and IP notifications.

The privacy page still identifies the full legal policy as pending. This update
adds a factual product explanation; it does not approve or replace that policy.

## Future copy preview — 9 September 2026

The local development UI and DEV and PROD demonstration deployments show the
following approved copy without a draft label:

> Your files are encrypted and automatically checked by AI.
> Share files through private links. Anyone with your link can access the shared file.
> Even fly.ae employees cannot read your files.

This is a wording preview, not a delivered security capability. The owner
confirmed on 9 September that PROD also serves as a demo and should show the same
copy without a draft label. Both deployment workflows set
`NEXT_PUBLIC_FUTURE_PRIVACY_COPY=true` at frontend build time. Builds without the
flag default to the factual access notice. The Privacy Policy page always
describes current capabilities.
