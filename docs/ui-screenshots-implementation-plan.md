# План: браузерные UI-тесты и скриншоты для desktop/mobile

Статус: план для передачи младшей модели, реализация не выполнена.
Дата: 2026-09-19.

## Задача исполнителю

Добавить к существующим проверкам fly.ae браузерные UI-тесты на Playwright Test. После падения теста пользователь должен найти PNG текущего экрана в известной папке и открыть HTML-отчёт с ошибкой и вложениями. Отдельная команда должна сохранять снимки ключевых состояний даже при успешных проверках. Поддержать desktop и мобильный размер окна в Chromium.

Существующие `node:test`, `jsdom` и backend-тесты сохраняются. Первый этап не включает пиксельное сравнение с эталонами, реальные устройства, дополнительные браузеры и развёртывание приложения.

## Что уже проверено в репозитории

- Корневой `npm test` вызывает `test:web`. Web-тесты сначала собирают приложение, затем запускают `node:test` через `tsx`.
- `apps/web/tests/document-library.test.mjs` содержит подходящие примеры данных и DOM-сценариев. Их можно использовать как образец, но файл регистрирует собственные тесты: импортировать его в Playwright нельзя.
- Локальный frontend запускается через `vinext dev`, конфигурация находится в `apps/web/vite.config.ts`. Есть интеграция Sites/Cloudflare и `.openai/hosting.json`; сохранять существующий способ запуска.
- Приложение восстанавливает авторизацию через `POST /api/v1/auth/session/refresh`. Access token хранится в памяти. Подстановка старой сессии в localStorage не обеспечит вход.
- На UI влияют `NEXT_PUBLIC_API_URL`, `NEXT_PUBLIC_MAINTENANCE_MODE` и `NEXT_PUBLIC_TEMPORARY_SHARE_ENABLED`.
- Имеющиеся GitHub Actions связаны с deployment. Для UI-проверок нужен отдельный workflow без AWS и deploy-шагов.
- `docs/user-paths.md` — реестр требований, а не доказательство автоматического покрытия. В нём есть устаревшие ограничения и статусы; сверять конкретные действия с текущим UI.
- На момент подготовки плана рабочая директория содержит чужие изменения, включая `README.md` и `infra/aws/template.yml`. Перед реализацией проверить `git status`; не перезаписывать их.

## Принятые решения

| Параметр | Решение |
|---|---|
| Раннер | `@playwright/test`, devDependency web-workspace |
| Браузер | Поставляемый Playwright Chromium |
| Desktop | project `desktop-chromium`, viewport 1440 × 900 |
| Mobile | project `mobile-chromium`, viewport 390 × 844, `isMobile: true`, `hasTouch: true` |
| Общие настройки | `deviceScaleFactor: 1`, светлая тема, `locale: en-US`, `timezoneId: UTC` |
| Сервер | Локальный frontend под управлением Playwright `webServer`, адрес `http://127.0.0.1:4173` |
| Данные | Изолированные API fixtures для каждого теста; backend и реальные учётные записи не нужны |
| Обычный запуск | `screenshot: only-on-failure`, `trace: retain-on-failure`, видео выключено |
| Просмотр экранов | Отдельная команда с `UI_SCREENSHOTS=1`, сохраняющая именованные контрольные снимки |
| Результаты | `<корень репозитория>/artifacts/ui/results/` |
| HTML-отчёт | `<корень репозитория>/artifacts/ui/report/index.html` |
| Повторные попытки | Первоначально `retries: 0`, чтобы причина падения оставалась очевидной |

Мобильный проект проверяет адаптивную вёрстку и touch-настройки Chromium. Это не проверка Safari/iOS или реального телефона. Скриншоты помогают увидеть дефект; без assertions или визуального сравнения раннер сам не распознаёт все ошибки дизайна.

## Порядок реализации

### 1. Зависимости, конфигурация и первый запуск

1. Прочитать актуальные `AGENTS.md`, package scripts, Vite-конфигурацию и UI-код. Зафиксировать исходные незакоммиченные изменения.
2. Добавить совместимую с проектным Node 22 версию `@playwright/test` в `apps/web/package.json`, обновить корневой `package-lock.json` штатной командой npm. Установить Chromium. Не использовать генератор, который заменит существующие файлы.
3. Создать `apps/web/playwright.config.ts`. Ограничить `testDir` каталогом `tests/ui`, чтобы новый и старый раннеры не подхватывали тесты друг друга. Для MVP использовать один worker.
4. Вычислять пути артефактов относительно файла конфигурации, а не текущей shell-директории. Включить reporters `list` и `html`; у HTML задать `open: never`.
5. Настроить `webServer` на существующий `vinext dev`. Сначала проверить поддерживаемые параметры через help локально установленной версии; задать host/port и запрет перехода на другой порт. `baseURL` и readiness URL должны совпадать. Таймаут старта — до 120 секунд, `reuseExistingServer: false`.
6. Передавать серверу тестовые значения: `NEXT_PUBLIC_API_URL=http://127.0.0.1:4173/api/v1`, `NEXT_PUBLIC_MAINTENANCE_MODE=false`, `NEXT_PUBLIC_TEMPORARY_SHARE_ENABLED=true`, `NEXT_PUBLIC_FUTURE_PRIVACY_COPY=false`. Проверить, что они действительно применились, а не были заменены локальным `.env`.
7. Начать с одного smoke-теста главной страницы в обоих проектах; только после успешного запуска расширять набор.

Нельзя автоматически переходить на установленный Chrome или менять приложение на другой runtime при проблемах запуска. Сначала диагностировать конфигурацию Vinext/Playwright. Этот набор проверяет локальный Vinext-rendering; паритет с AWS static export — отдельная задача.

### 2. Тестовые данные и взаимодействие с API

Создать `apps/web/tests/ui/fixtures.ts`, экспортирующий расширенный Playwright `test` и `expect`.

- Регистрировать `context.route` до первой навигации, блокировать Service Workers для предсказуемого перехвата.
- Разрешить загрузку реального frontend с локального сервера. Все запросы к `/api/v1/**` обслуживать тестовыми ответами с правильными HTTP-методами и статусами.
- Для анонимного сценария refresh возвращает 401; для авторизованного — валидную структуру session с заведомо тестовым токеном. Использовать текущие поля из `auth-session.ts`.
- Подготовить категории, документы APPROVED/PROCESSING, share-ответы и нужные ошибки. Даты, ID и имена файлов сделать постоянными. Состояние коллекции документов изолировать на уровне теста.
- Авторизацию, пустой список, ошибку загрузки списка, OTP-ошибку и невалидную share-ссылку выбирать через настройки fixture. Не подменять React-компоненты: тест должен видеть настоящее приложение и CSS.
- Неизвестный API-вызов должен давать понятную диагностику и проваливать тест; не отвечать универсальным пустым 200. Не пропускать запросы на реальный backend.
- Неожиданные внешние обращения блокировать и фиксировать. Шрифты/изображения, необходимые для UI, проверить отдельно и обеспечить воспроизводимыми локальными ресурсами или явно заданной подменой.

### 3. Скриншоты и диагностика

Создать небольшой helper `captureCheckpoint(page, testInfo, name)`:

1. При отсутствии `UI_SCREENSHOTS=1` ничего не делает.
2. Дожидается готового состояния через assertions в вызывающем тесте; перед снимком ждёт `document.fonts.ready` и завершения загрузки существенных изображений.
3. Сохраняет PNG через `testInfo.outputPath(...)`, затем прикрепляет его через `testInfo.attach`. Это сохраняет уникальность для проекта, теста и попытки.
4. Использует понятные имена: `01-upload-home.png`, `02-login-error.png`, `03-library.png`. Для контрольных снимков — `fullPage: true`, выключенные анимации и скрытый caret.

Скриншот падения оставлять встроенному механизму Playwright. Он должен работать и без `UI_SCREENSHOTS=1`, в том числе если тест упал раньше контрольной точки. Для него достаточно viewport-снимка: он показывает видимую пользователю область на момент ошибки. Не закрывать `page` вручную до сохранения встроенных артефактов.

При падении также сохранять короткий текстовый лог `pageerror`, ошибок browser console и неожиданных API-запросов через attachment. Ожидаемые HTTP-ошибки негативных сценариев не считать отдельным дефектом. Не допускать, чтобы ошибка записи дополнительного лога скрыла исходное падение.

Playwright создаёт отдельные подпапки тестов; в имени папки должен различаться desktop/mobile. Пример ожидаемого результата, без требования к точному внутреннему имени Playwright:

```text
artifacts/ui/
  results/
    ...UI-001...desktop-chromium/
      01-upload-home.png
    ...UI-003...mobile-chromium/
      test-failed-1.png
      trace.zip
      browser-errors.txt
  report/
    index.html
    ...данные и вложения HTML-отчёта...
```

Локальные папки содержат последний запуск. Указать в инструкции, что следующий запуск обновляет их. Не писать собственную очистку всей папки `artifacts`: там уже могут находиться пользовательские файлы.

### 4. Минимальный набор сценариев

Каждый сценарий ниже запускается в обоих проектах; обязательный минимум — 8 сценариев × 2 проекта = 16 проверок. Использовать стабильные ID в названиях тестов.

| ID | Действие и проверка | Контрольный снимок |
|---|---|---|
| UI-001 | Открыть главную без сессии; дождаться категорий; проверить форму и основной CTA | Главная загрузки |
| UI-002 | Открыть вход через видимые элементы desktop/mobile; проверить поле email и кнопку отправки | Диалог входа |
| UI-003 | Отправить email, получить mock 429 с Retry-After; проверить сообщение и возможность закрыть диалог | Диалог с ошибкой |
| UI-004 | Восстановить тестовую сессию; открыть My Documents; проверить категории и загруженные данные | Библиотека документов |
| UI-005 | Пройти категория → папка → документы; проверить breadcrumbs и возврат | Содержимое папки |
| UI-006 | Открыть меню действий у папки рядом с краем окна; проверить, что bounding box меню внутри viewport | Открытое меню |
| UI-007 | Получить ошибку API загрузки My Documents; проверить сообщение, нажать доступный Retry, вернуть успешный ответ | Ошибка и восстановленная библиотека |
| UI-008 | Открыть невалидную публичную share-ссылку; mock 404; проверить понятное сообщение без требования входа | Ошибка share-ссылки |

Для UI-002/UI-004 в мобильном проекте идти через настоящее мобильное меню. В desktop пользоваться видимой навигацией. Не кликать скрытые элементы через `force: true`.

Локаторы — преимущественно `getByRole`/`getByLabel`, с уточнением области, если есть скрытые дубликаты. Не привязываться к DOM-индексам или сгенерированным CSS-классам. Ожидания — web-first assertions; не добавлять фиксированные sleep для стабилизации. Для основных экранов проверить отсутствие общего горизонтального переполнения; таблицы с намеренным внутренним scroll-контейнером оценивать отдельно.

Если конкретный сценарий выявил дефект продукта, сохранить артефакты и описать его. Не ослаблять проверку и не расширять задачу до большого UI-рефакторинга. После MVP можно отдельно добавить успешный share/QR и guest upload; полный multipart-flow не нужен для внедрения механизма снимков.

### 5. Команды и документация

Добавить scripts web-workspace и делегирующие команды в корневой `package.json`:

| Корневая команда | Назначение |
|---|---|
| `npm run test:ui` | Оба проекта, скриншоты при падениях |
| `npm run test:ui:desktop` | Только desktop-chromium |
| `npm run test:ui:mobile` | Только mobile-chromium |
| `npm run test:ui:screenshots` | Оба проекта, контрольные PNG даже при успехе плюс PNG падений |
| `npm run test:ui:report` | `playwright show-report` для корневой папки отчёта |

Сохранить смысл существующих `npm test` и `test:web`. Новый набор запускается явно и отдельным CI-job. Проверить пути и команды именно из корня репозитория.

Создать `docs/ui-testing.md`: установка браузера, команды, расположение PNG, открытие отчёта, просмотр trace, обновление последних результатов, способ добавления сценария. Короткую ссылку в README добавить точечной правкой с сохранением чужих изменений.

Добавить в `.gitignore` только `/artifacts/ui/`, а не весь `/artifacts/`. При необходимости исключить генерируемые файлы из lint; не исключать сами тесты. Проверить совместимость Playwright TS-файлов с существующим `tsconfig` и сборкой.

### 6. CI без deployment

Создать `.github/workflows/ui-tests.yml` для `pull_request` с релевантными path-фильтрами и ручного `workflow_dispatch`.

- Минимальные permissions: `contents: read`; без AWS credentials/environments/secrets.
- Установить Node, совместимый с текущим проектом и выбранным Playwright; выполнить `npm ci`.
- Установить Chromium с системными зависимостями: `playwright install --with-deps chromium` через web-workspace.
- Запустить `npm run test:ui:screenshots`, чтобы CI давал снимки и успешных экранов.
- Загружать всю `/artifacts/ui/` через upload-artifact с `if: always()`, срок хранения 14 дней. Не терять исходный ненулевой exit code тестов.
- При отсутствии файлов после ошибки установки выдавать понятное предупреждение; если браузер не запустился, скриншота страницы быть не может.
- Workflow не запускает существующие deploy-workflows. Публикация/запуск удалённого workflow не является частью локального внедрения, если пользователь отдельно этого не поручил.

## Проверка готовности

1. `npm run test:ui` автоматически запускает frontend и выполняет 16 проверок; сервер корректно останавливается после прогона.
2. `npm run test:ui:screenshots` создаёт именованные PNG обоих проектов. Открыть несколько PNG и убедиться, что это настоящий UI с данными, а не loader или пустая страница.
3. Временно добавить заведомо неверное assertion после успешного открытия главной. Запустить этот тест в обоих проектах обычной командой, без `UI_SCREENSHOTS=1`: получить ненулевой exit code, screenshot и trace для каждого проекта. Удалить только добавленную диагностическую проверку; не оставлять падающий тест в итоговом коде.
4. Перед повторным зелёным прогоном просмотреть эти PNG, открыть HTML-отчёт и проверить доступность вложений. Убедиться, что размеры failure PNG соответствуют 1440 × 900 и 390 × 844.
5. Повторить обычный UI-прогон после удаления диагностического assertion. Выполнить `npm run test:web` и `npm run lint`; проверить, что исходный набор продолжает работать.
6. Убедиться, что сценарии выполняются без запущенного backend и не обращаются к production. Проверить, что артефакты игнорируются git, а чужие файлы/изменения сохранены.
7. В итоговом отчёте исполнителя указать команды, количество пройденных проверок, путь к PNG/HTML и ограничения. Явно отличить локально проверенное от ещё не запущенного CI.
